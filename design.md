# Orchestrator — Design

[Home](README.md)

---

**Status:** design (not yet built) · **Verified against:** Claude Code `2.1.183`

A local, autonomous agentic system that dispatches work described in GitHub issues, verifies it, and surfaces only the decisions that need *you* — so your time goes to research judgment instead of babysitting a session and hitting "1".

## The problem this solves

Today: you babysit a single Claude session — mostly waiting, approving tool calls — and to fill the waiting you open more sessions in other projects, paying a heavy **cross-project context-switch** cost (pesticides → solar is the expensive swap). The goal is to invert that: agents grind in the background while you do value-add work, and you engage in batched, per-project review windows.

## Core principles

These are the load-bearing decisions; everything below follows from them.

1. **GitHub is the only source of truth.** Issues, PRs, labels, comments, board fields. Every other artifact (ledger, logs, inbox view) is a disposable derivative regenerated from GitHub. A crash loses nothing.
2. **Intent is yours; context is the repo's.** An agent booted in a repo inherits its `CLAUDE.md`, code, and data for free (context). It cannot infer *what you want and what counts as done* (intent). So **authoring issues is always you**; agents only execute issues that already carry a contract.
3. **Deterministic gathering, model judgment.** Cheap scripts (`gh` + `jq`) collect and bucket board state; tokens are spent only on judgment (what to dispatch, whether work is correct). Same philosophy as RTK.
4. **Fresh-wake, durable-state.** The orchestrator holds no long-lived context. It wakes, rebuilds state from GitHub + a small local ledger, acts, exits. No compacting fragile context across time.
5. **Raw data is sacred.** Each repo's `raw/` is read-only — even to you. Everything downstream is deterministically regenerable from code, so the blast radius of any rogue worker is "redo some compute," never "lose data."
6. **Human merge gate, always.** A passed PR enters your inbox awaiting *your* merge. You are a research advisor evaluating outputs and asking probing questions — not a line-by-line code reviewer. **The gate is on the decision, not the keystroke** *(sharpened 2026-08-02, #48)*: no agent ever merges on its own initiative, but the *mechanics* are delegable — the human-gated interactive orchestrator may run the merge when you instruct it in-session naming the PR (see Safety model). The autonomous loop never merges under any condition; there is no operator present to instruct it.
7. **Group by project, not by task.** Your scarce resource is domain attention; the inbox clusters everything for one project so you load a domain once and clear it.

## Actors

| Actor | Lifespan | Context | Driver | Job |
|---|---|---|---|---|
| **Orchestrator** | standing (scheduled), local | board-only (no science) | `launchd` + you | Route the ball: intake-gate issues, dispatch workers/checkers, maintain the ledger |
| **Worker** | ephemeral, in-repo | deep (booted from repo) | orchestrator | Implement one issue → draft PR with results summary → signal ready or escalate |
| **Checker** | ephemeral, in-repo | deep | orchestrator | Verify a ready PR against the issue's acceptance criteria |
| **Advisor console** | interactive, in-repo | deep | **you** | Author/remediate issues, review PRs, ask probing questions, post answers |
| **You** | — | — | — | Write the playbook (issues), make research judgments, merge |

Workers, checkers, and the advisor console are **the same boot recipe** — a fresh Claude in repo X with its `CLAUDE.md` + the relevant issue/PR. Only the role and driver differ. There is exactly **one standing component** (the orchestrator); everything else is ephemeral or interactive. No standing per-project managers — cross-issue sequencing lives as issue dependencies + sprint planning.

## How a session is assembled (boot recipe)

Mechanically, every worker/checker/console session is one `claude` invocation composed from markdown + flags:

- **Project context** — the repo's `CLAUDE.md` auto-loads when the session boots in the repo.
- **Role brief** — an editable markdown file (`briefs/worker-brief.md`, `briefs/checker-brief.md`, `briefs/orchestrator-brief.md`): the protocol layer (lifecycle, signals, results-summary contract). The launcher renders it — strips the header comment, fills `{{TOKENS}}` from the manifest/PR — and passes the result via `--append-system-prompt`. Briefs live in files (not heredocs) so they're easy to edit without touching the launcher.
- **The task** — the issue, fetched at runtime (`gh issue view N`) or passed as the user prompt.
- **Task know-how** — the relevant **skill** (see Skill library), selected by matching the issue's **Type** field.

So: repo `CLAUDE.md` (auto) + role brief (appended file) + issue (fetched) + skill (invoked). The brief stays short because the skills carry the detail.

## The loop — "route the ball"

The orchestrator's entire job is routing one ball, observed each wake from GitHub state:

- **Ball in worker's court** → dispatch/continue a worker. Triggers: a new well-specified issue; your *answer* to an escalation; your *probing question* on a PR.
- **Ball in checker's court** → a PR marked **ready** → dispatch a checker.
- **Ball in your court** → `needs-input` (a question) or a checker-passed PR (awaiting merge) or `needs-definition` (under-specified issue). This is your **inbox**.

Your probing question and a worker's escalation are the *same mechanism in opposite directions*: a human comment (content) + a label flip (signal) puts the ball back in the worker's court.

## Worker lifecycle & signals

A worker runs to completion and exits in exactly one state, signalled on GitHub (no board-status changes needed):

- **Still working** → draft PR open. (No signal.)
- **Ready for review** → worker marks the PR **ready** (un-drafts). Orchestrator → dispatch checker.
- **Needs input** → worker adds `needs-input` + a question comment, leaves PR draft. Orchestrator → inbox.
- **Ran out of budget / rate-limited / crashed (a hard stop)** → no clean exit, so no `/handoff` and no Stop-hook nudge — `finalize_dispatch` (in `bin/dispatch-common.sh`) does the cleanup instead: pushes any local commits immediately (don't wait for a future redispatch to find them), records `interrupted-*` in the ledger, and posts a `**Worker interrupted: <status>` comment on the issue. `bin/board-digest.sh` treats a draft PR with no live worker as the worker's court structurally — no label required — so it's redispatched next cycle automatically. If it keeps happening, `WORKER_LIMIT` (default 4 consecutive interruptions, mirrors `CHECKER_LIMIT`) escalates it to `needs-input` instead of retrying forever. *(This replaced an earlier, never-implemented "retries once" design — see git history around 2026-07-01.)*

**Compute persistence — the complement to the hard-stop handling above.** `finalize_dispatch` rescues *commit* state when a worker dies, but in-flight *compute* (a multi-hour estimation kicked off inline) dies with the process. `bin/tmux-run.sh` (invoked `dr tmux-run <repo-slug> <issue> -- <cmd>`) closes that gap: a worker runs any long command detached through the wrapper, which derives a session name that is a pure function of the task — `derail-<owner-repo>-<issue>` (the manifest's `repo:` with `/`→`-`, issue only, no timestamps/PIDs) — so the run survives worker death and the next worker reattaches instead of restarting from zero. The wrapper is the single, canonical place that derivation lives, which also resolves the old `<repo-slug>` ambiguity (the *session* name uses `owner/repo`, but the wrapper's first arg is the manifest key, e.g. `distance-decay-est`). The canonical name doubles as a cross-worker mutex: the wrapper's atomic `tmux new-session` succeeds for exactly one worker; a second worker's create fails on the name collision, and the wrapper reports the existing session (`status=exists-alive|exists-dead`) rather than spawning a colliding duplicate — no `has-session`-then-create race. **The wrapper is mechanical only** — it does the mutex and reports status; the *worker* makes every semantic call (are outputs present? is the code stale?) and does any `tmux kill-session` teardown. The durable log is anchored to the manifest's `data_root` at `data_root/logs/derail-<owner-repo>-<issue>.log` — outside the prunable worktree and recomputable from slug+issue without reading the comment. **A budget-capped worker cannot busy-wait**: on finding a still-running session it exits cleanly and leaves it running (it would only burn budget sitting idle, then get killed) — the next dispatch reattaches. Consistent with "GitHub is the only source of truth," the runtime session record is a **comment** on the issue/PR (session name, `dr tmux-run …` command, durable log path) — never a local state file, since the name is recomputable and `tmux ls` is the runtime truth for liveness.

## The results-summary contract

Every finished PR's description must let you advise *without reading the diff*. Required sections (the checker enforces they exist and the outputs are real):

- **Goal** — what the issue asked for.
- **What I did** — 2–3 sentences.
- **What I ran** — script/command, reproducible.
- **Key outputs** — the actual table/figure/numbers, committed and *shown*, not "see code." Exact form is defined per-issue (a cleaning task ≠ a robustness task ≠ a lit review).
- **Judgment calls / open questions** — so your probing questions have somewhere to land.
- **Outcome** — a typed self-report of what happened: `shipped` (a change satisfies the issue), `no-op` (the issue was already satisfied / a dup — nothing to change, here's why), or `blocked` / `handed-off` (couldn't finish — paired with `needs-input` or a `/handoff` state comment). Gives the digest and checker a structured signal instead of inferring intent from a draft/ready bit alone — and makes the "nothing needed doing" case a first-class, non-suspicious result. *(Adapted from Gas City's typed `work_outcome`.)*

The per-task output expectations are defined **in the issue's acceptance criteria** at authoring time — which is why good issues are core to your job.

**Enforced by a `Stop` hook, not just the brief** *(added 2026-06-21)*. The brief tells a worker to leave a trail; a hook makes it mechanical. `host/hooks/worker-stop-guard.sh` (a `Stop` hook injected per-worker by `bin/launch-worker.sh` via `--settings`, with the issue # and repo baked into its command) refuses to let a worker session end unless it has finished *legibly*: either a **PR exists for its branch** (shipped/working) or the issue carries **`needs-input`** (blocked/escalated). Otherwise it returns `{"decision":"block"}` with a reason that re-states the two exits, and the worker keeps going. It's a **single firm nudge** — the hook honors `stop_hook_active` (the documented guard against Stop-hook loops), so it blocks at most once; a worker that ignores the nudge is caught downstream (no PR → invisible to the digest/checker) rather than trapped burning budget. Scoped to workers only — checkers have a different contract (no Edit/Write, they don't open PRs).

## Checkers

Verification is a single **LLM checker at PR-ready** (the deliberate signal): substantive verification against the issue's acceptance criteria plus output sanity — re-running/inspecting real outputs, not trusting the PR's claim. It triggers on **PR marked ready**, not on commit frequency.

*(A deterministic per-push GitHub Actions CI tier was considered and dropped: the data model is machine-local and gitignored, so a cloud runner has no data to run the analysis against — CI could only do static parse/lint checks, which aren't worth the per-repo wiring and private-repo minutes. The mechanical "does it run on real data" check stays local, where the worker and checker both have the data.)*

**Route by whose court the follow-ups are in, not just by pass/fail** *(decided 2026-06-20)*. The checker first tags each finding with an `actor` — `worker` (a concrete fix: bug, unmet criterion, cleanup, a doable improvement) or `operator` (a research-judgment call / FYI only Emmett can settle). Then: **pass** (criteria met, no findings) and **pass_with_findings** (criteria met; *every* remaining finding is `actor=operator`) → your merge gate; **changes_requested** (≥1 `actor=worker` finding, even if criteria technically pass) and **fail** (criterion unmet) → `resume` (worker takes another pass); **blocked** → `needs-input`. The crucial rule: an `actor=operator` finding is **never** bounced to a worker — so once the worker has ground down all the worker-actionable items, only Emmett's calls remain → `pass_with_findings` → his court, and the loop terminates on its own. A `CHECKER_LIMIT` (default 4 rounds) is a pure backstop against a runaway worker↔checker ping-pong: if it's ever hit, the orchestrator escalates the PR to `needs-input` rather than re-checking forever. Rounds are counted **per review generation, not over the PR's lifetime** *(fixed 2026-06-22)* — a `pass`/`pass_with_findings`/`blocked` verdict hands the ball to Emmett and ends a generation, so once he reviews and bounces it the next check is round 1 again. (Counting lifetime verdict comments wrongly tripped the limit on a PR that had legitimately round-tripped through Emmett's court several times.)

**Signalling is by issue label + comment, not by GitHub review** *(decided 2026-06-20)*. The checker authenticates as the same account that authored the PR (the worker uses Emmett's `gh`), and GitHub refuses to let an account formally approve / request-changes on its **own** PR. So the checker never posts a formal review verdict — it posts its verdict as a **comment** (led by `**Checker verdict: <verdict>**` so rounds can be counted) and sets an **issue label**: `checked-pass` (criteria met → Emmett's merge gate; PR left ready), `resume` + un-ready (worker-actionable changes), or `needs-input` (blocked). Routing labels live on the **issue** (matching `resume`/`needs-input`), so the digest classifies a PR by its closing issue's labels. **The checker never merges** — merging is always Emmett's. (A genuine second-identity bot PAT, which *could* post real approvals, was considered and deferred as unnecessary overhead for a solo researcher.)

**Structured verdict (so the orchestrator routes deterministically).** The checker emits its review as a small JSON object alongside the prose comment — `verdict ∈ {pass, pass_with_findings, changes_requested, fail, blocked}`, `findings[]` (each `severity` / `actor` / `title` / `file` / `line`), `evidence` (commands run / files inspected), and `failure_class ∈ {none, transient, hard}`. `verdict` maps to label/PR-state without parsing prose: `pass`/`pass_with_findings` → `checked-pass` (merge gate), `changes_requested`/`fail` → `resume` + un-ready, `blocked` → `needs-input`. *(Pattern adapted from Gas City's `mol-review-quorum` lane contract.)*

**The verdict file is rotated at dispatch, so a re-dispatched checker can't report a stale verdict** *(issue #49, 2026-08-03)*. `bin/launch-checker.sh` writes that JSON to `logs/<slug>-pr-<n>-verdict.json` — a path fixed per (slug, PR), with **no round/generation/timestamp component** — and nothing ever removed it. `bin/watch-dispatch.sh`'s `terminal_state` stats that file *before* consulting the ledger status, so on a round-2+ dispatch the **previous** round's verdict was present from tick one and won: observed on PR #46 (2026-07-31) reporting `pass_with_findings` seconds after dispatch, off round 1's head three commits stale, while the checker pid was still alive and the real verdict — `changes_requested` — landed 3.5 minutes later; and again on PRs #57/#58 (2026-08-03), where two Saturday verdicts would have been surfaced as that night's on trees no checker had yet seen. The reporting error is the smaller half. The larger one is that the briefs promise, in bold, that *"a crashed or interrupted dispatch is never watched in silence"* — and with a stale file present, a round-2 checker that dies **before writing anything** is reported as a clean verdict and the crash never surfaces, i.e. `checked-pass` on an unreviewed tree, exactly what the merge gate exists to prevent. The fix is one line at dispatch: `rotate_verdict_file` (in `bin/dispatch-common.sh`, called by `launch-checker.sh` after the `--dry-run` exit and before either the detached or `--foreground` path) `mv -f`s any existing verdict to a single `<…>.prev.json` slot, so the canonical path is **absent** when a generation starts. Blast radius is deliberately nil elsewhere: `watch-dispatch.sh` is untouched and keeps reading only the canonical path (`.prev.json` is invisible to it), and neither `orchestrator-cycle.sh` nor `board-digest.sh` ever reads the file — all routing is label-driven, and labels are applied by the checker itself, so the autonomous loop was never misled by this. **Rejected alternatives:** a bare `rm` (a re-dispatched checker already overwrote its predecessor in place, so no history is lost either way — *except* in the one case that motivates the fix, a fresh checker crashing before its first write, where the displaced file is the only local copy; moving costs nothing and keeps that copy), and a timestamped archive (nothing prunes `logs/`, so it would grow unbounded, and the checker's PR comment already carries the full verdict JSON — comments never overwrite, so **GitHub holds every round**; `logs/` are disposable derivatives).

**Checkers give feedback, never do the work — enforced mechanically:** a checker boots with a restricted tool set (`Read`, `Bash` to run tests/inspect, `gh` to comment + set labels) and **no `Edit`/`Write`**. It literally cannot modify code. **Belt-and-suspenders:** the checker records a mutation baseline (`git status --porcelain`) on entry and again before exit, and reports the delta — so a clean checker run *proves* it touched nothing, and any accidental write surfaces instead of riding along into the PR.

**Checker ↔ worker communication is asynchronous, through GitHub** (the worker has already exited): the checker posts PR review comments; the orchestrator re-dispatches a worker on `resume` that `/pickup`s, reads them, and addresses them — the same comment-is-content / label-is-signal handshake as your own review.

## Wake digest + hook

A deterministic script `bin/board-digest.sh` (`gh project item-list 3 --owner @me --format json` + `jq`) emits a compact markdown digest grouped by the board **Status** field, annotated with **Project** and **Repository**, plus computed buckets: **ready-for-review PRs**, **needs-input issues**, **resume issues**, **needs-definition issues**, and a diff against the ledger (what's in-flight). `Done` is capped to "closed in last N days" and ignored for dispatch.

The digest is injected via an **env-gated `SessionStart` hook** (`ORCHESTRATOR=1`) so the orchestrator boots pre-loaded with board state and zero tool calls — and so it never fires in your normal interactive sessions. The script **reports**; the orchestrator **decides** what to dispatch (judgment stays in the model).

## State & durability

- **Truth:** GitHub (issues/PRs/labels/comments/board).
- **Ledger:** `ledger.md` — the one thing GitHub doesn't record: `issue # → branch / log path / pid / dispatched-at / status`. Used to avoid double-dispatch, count concurrency, and detect crashes. Worker lines are `- #N | …`; checker lines `- check pr#N | …` (the leading form keeps checkers out of the worker concurrency-count regex). `status ∈ {dispatched, done, incomplete-*, interrupted-*}` (plus `unknown` when the log carries no parseable result JSON) — set to `dispatched` at launch and flipped by the launcher's post-run `finalize_dispatch` (see below). The two failure families are deliberately distinct and both prefix-matchable: `interrupted-{ratelimit,budget,error}` = the session was **cut off**; `incomplete-{waiting,uncommitted,unpushed,nopr,draft,conflicting,noverdict}` = the session **exited cleanly but finalized nothing usable**. `done` therefore means *actually finalized*. `bin/ledger-prune.sh` drops closed-issue / dead-pid entries at the start of every cycle and, when it drops one whose status is `interrupted-*` **or `incomplete-*`**, says so (so neither a cutoff nor an unfinished run is silent). Since issue #63 it **reconciles before it prunes**: a dead-pid line still reading `dispatched` never reached `finalize_dispatch` at all, so the prune pass re-runs that finalization from outside the dead process, writes the resulting status to the line, and only then decides whether to drop it — and a line dropped while still non-terminal names itself, its log, and whether a verdict file was found (see below).

> **Liveness caveat — `remain-on-exit`.** The invariant is that **a finished `derail-*` run leaves an inspectable dead session**: that is what makes liveness decidable at all — `absent` means "never ran / already reaped", `dead` means "ran and finished, here's its pane and log". So anything deciding whether a detached job is still running (`tmux_job_state` in `bin/dispatch-common.sh`, the digest's `⏳ tmux-live` probe) must read `#{pane_dead}`, **never `tmux has-session` alone**: `bin/tmux-run.sh` sets `remain-on-exit on` so a finished job's session lingers for the next worker to inspect, and a has-session-based check would report every completed-but-not-torn-down run as live forever, pinning healthy workers to `incomplete-waiting`. Holding that invariant requires the option to be armed **in the same `tmux` invocation that creates the session** (`new-session … \; set-option -w … remain-on-exit on`, issue #54, 2026-08-02) — tmux runs a command list to completion before its event loop reaps the pane's exit, whereas across two calls a command that exits in milliseconds destroys its window in the gap and the whole session vanishes, collapsing `dead` into `absent` for exactly the fast runs. Holding it *also* requires the fallback for a tmux too old to accept `-w` to be a **second complete `new-session … \; set-option …` list**, not a second `set-option` appended to the first list: tmux **parses a whole command list before executing any of it**, so an unknown flag rejects the list wholesale and `new-session` never runs — a fallback inside the same list is unreachable, and the create is lost (the dispatch would then hit the "no such session (tmux error)" `die`, i.e. failing to arm the option would fail the dispatch). Re-issuing the create with the version-agnostic session-scoped form keeps it best-effort, and the ownership call is untouched: in a real collision **both** attempts fail on the name and create nothing, so create-fails-plus-session-exists still means another worker owns it.
- **Logs:** `logs/<slug>-issue-N.log` / `-pr-N.log` — each session's stdout, for *your* debugging. The durable record is the PR.
- **Worktrees:** `<worktrees_dir>/issue-N` (per-project, from the manifest) — one per dispatched issue, created idempotently by `bin/launch-worker.sh` and *reused* across re-dispatches (so an interrupted worker's local commit is found and pushed next cycle). They are pure derivatives (principle #1/#4) and can be large (a checked-out repo plus generated outputs — a single merged solar-income worktree measured ~7 GB), but nothing reclaimed them, so the dir grew without bound as branches merged. `bin/worktree-prune.sh` reclaims them in **two modes**:
  - **`--auto`** (run first in every cycle, beside `bin/ledger-prune.sh`) — non-interactive, deletes a worktree only when its work is **provably on the default branch**: its branch has a **merged PR**. That merged bit is the authoritative signal *precisely because git ancestry isn't* — a squash merge leaves the branch tip unreachable from `main`, so `git merge-base --is-ancestor` would wrongly say "unmerged." Anything **not merged** — even a closed-not-planned issue — is **kept and reported**, never auto-deleted; auto mode will not touch work that didn't land on `main`.
  - **interactive** (the default when run raw, needs a terminal) — lists every worktree with disk use and status (✓ merged+clean vs. · needs-confirm), and you pick which to remove. You *can* delete an unmerged or in-flight one, but it takes a per-item `y/N` confirmation that names the risk.

  **`--auto` also reaps dead `derail-*` tmux sessions** *(issue #53, 2026-08-02)*. Second derivative, same instinct: `bin/tmux-run.sh` sets `remain-on-exit on` so a *finished* detached job's session lingers as a dead pane for the next dispatch to inspect (load-bearing — see the liveness caveat above), and nothing ever cleared them afterwards, so a worker that exits-to-wait and is never re-dispatched left its session for the rest of the machine's uptime. Bounded rather than unbounded (the tmux server dies on reboot) but not free: `board-digest.sh` walks every session once per digest. The reaper's whole content is its safety rule — an **alive** session means a worker is legitimately waiting on real compute (an R estimation), and killing it destroys exactly the kind of work GitHub does *not* have, which is the same invariant the worktree half protects. So a session is killed iff **both** its name starts with `derail-` (anything else on the machine is not ours) **and** `tmux_job_state` says `dead` — liveness, never "the issue looks finished." A live session is reported (`keep tmux <name> — pane alive`) and left; **`--force` does not extend to tmux**, deliberately, because there is no untracked-files-style "safe override" here, only destroyed compute. Liveness is `tmux_job_state` **sourced from `bin/dispatch-common.sh`**, not a second probe: a reimplementation is free to drift, and the drift direction that matters (toward `has-session`, or toward "the run looks done") is the one that starts killing live jobs. No `tmux` on PATH or no server running is a clean no-op — the tmux summary line is suppressed entirely rather than printing a meaningless `0/0`, so the pruner stays quiet on a machine that never ran a detached job. Interactive mode deliberately does *not* touch the tmux server (nothing to pick, nothing to confirm). Covered by `tests/offline/test-worktree-prune.sh` against a **private tmux socket** (`TMUX_TMPDIR`), so the suite can never see — let alone kill — a real session.
  
  The guarded invariant in both modes is the one thing a worktree can hold that GitHub can't — **local-only state** (uncommitted edits, unpushed commits): auto mode refuses on it outright; interactive mode surfaces it and makes you confirm. It also skips a live in-flight worktree (a matching ledger line). On removal it drops the now-orphaned local branch (`branch -D` — squash-merge defeats the safe `-d` test). **`--force` (auto only)** overrides *one* thing: a removal blocked solely by leftover **untracked, non-gitignored** files (stray outputs) — it never overrides uncommitted edits or unpushed commits. Recovery if ever wrong is free: a re-dispatch recreates the worktree from `origin`. *(Portability landmine, fixed 2026-06-22: macOS ships **bash 3.2**, where expanding an **empty array** under `set -u` — e.g. `"${flag[@]}"` when no `--force` — is a fatal `unbound variable` error; it silently aborted every removal. These scripts must branch on the flag rather than build-then-expand an optional-arg array.)* *(Two coupled bugs fixed 2026-07-17, issue #23. (1) `compute_status` ended on a bare `[ "$FORCE" = 1 ] && ST_SAFE=1` short-circuit — **false** in the merged+untracked+no-`--force` case — so the function returned nonzero and `set -e` aborted the whole `--auto` run before printing anything (silent exit 1); fixed with an explicit `return 0` so a helper never leaks a trailing conditional's status. (2) The untracked files that tripped it were themselves spurious: **both launchers** (`bin/launch-worker.sh` and `bin/launch-checker.sh`) scaffold a default `data/results` + `data/raw` symlink whenever `raw_resolved` is set, but a **code-only** manifest — derailleur self-hosted — deliberately points `raw_resolved` at the repo root itself (for a valid `--add-dir` + blanket deny-hook coverage, not a real data tree), so the launcher created a self-referential `data/raw -> <repo>` symlink that never belonged on a code repo and lingered untracked. Fixed by skipping the default scaffold when `raw_resolved` resolves to the same real path as `working_clone`.)*

**Interruption is detected, not assumed-success** *(added 2026-06-20)*. `claude --output-format json` can exit with `subtype:"success"` yet `is_error:true` + `api_error_status:429` ("session limit") — a rate-limit cutoff that leaves work **committed locally but unpushed**. So a single shared `finalize_dispatch` (in `bin/dispatch-common.sh`, sourced by both launchers) runs when the session exits: it `classify_result`s the real fields (rate-limit / budget / error / clean), records the verdict in the ledger `status`, and on interruption (worker only) pushes any commits ahead of upstream immediately — rather than waiting for a future redispatch to find them — and posts a `**Worker interrupted: <status>` comment on the issue. **Recovery is automatic and needs no label to survive** *(revised 2026-07-01 — see below)*: `bin/board-digest.sh` treats a draft PR with no live worker as the worker's court purely from PR + ledger state, so the next cycle redispatches it regardless of whether any label was ever set. `WORKER_LIMIT` (`bin/ledger-prune.sh`, counting consecutive `**Worker interrupted:` / `**Worker incomplete:` comments) stops that from looping forever on an issue that can never finish unattended.

**A clean exit is not a finish: exit-to-wait records `incomplete-<reason>`** *(issue #40, 2026-07-31)*. The detection above answers "was the session cut off?" — a *different* question from "did it finalize anything?" A worker that hands a long run to `dr tmux-run` is told by its brief to **exit cleanly** and let the next dispatch reattach; that is exit-0, so `classify_result` said `done`, and `done` reads as "finalized" to every downstream consumer. Observed: `logs/solar-income-pr-38.log` ended "…executing in the background…" with no verdict written, and `logs/solar-income-issue-3{3,4}.log` ended "…wait for the background waiter…" — all three recorded `done`. Worse, an exit-to-wait produced **neither** countable comment, so it was invisible to `WORKER_LIMIT` *and* `CHECKER_LIMIT`: a wedged job re-dispatched every cycle indefinitely at a full budget a round with no path to `needs-input`.

Fix — `classify_result` stays a pure log-JSON parser (the two questions stay separately testable), and a new `assert_finalized` is consulted **only** when it returns `done`, naming the first unmet check: worker `waiting → uncommitted → unpushed → nopr → draft → conflicting` (the last rung added by issue #51, below), checker `waiting → noverdict`. The status becomes `incomplete-<reason>`, which reuses the interrupted path's immediate unpushed-commit push and posts `**Worker incomplete:` / `**Checker incomplete:`. Both caps then count it — see the split below on the worker side, and `CHECKER_LIMIT`'s `NROUNDS` counts incomplete rounds alongside verdicts (and, since #52 below, interrupted ones), though only a to-operator verdict still ends a review generation. Three deliberate **non-goals**: no tmux gate on worker dispatch (re-dispatch *is* the intended reattach-and-babysit, and `tmux-run.sh`'s atomic create is already the mutex — a `has-session` probe would only add a race), no tmux gate on checker dispatch (PR-ready remains the sole trigger; an exited-to-wait worker leaves the PR draft, which already gates it), and no false `incomplete` from a flaky network (a failed or unparseable `gh` lookup skips the `nopr`/`draft` checks with a stderr note; only local, deterministic signals may assert a reason). Visibility, not gating: `board-digest.sh` marks live jobs `⏳ tmux-live <session>` from one `tmux list-panes -a` probe per digest, and `watch-dispatch.sh` reports `incomplete-*` as terminal with `(re-dispatch required)`. Covered by `tests/offline/test-finalize-complete.sh`, whose load-bearing case is a session with `pane_dead=1` still classifying `done` — see the `remain-on-exit` caveat above.

**The no-clean-finish cap is split by reason, priced by retry cost** *(issue #40 amendment, 2026-07-31)*. Counting exit-to-wait against `WORKER_LIMIT` closed the escalation hole but over-corrected: a worker babysitting a legitimately long detached run posts `**Worker incomplete: incomplete-waiting` *every* round by design, so four rounds of honest multi-session progress escalated as a malfunction. `bin/ledger-prune.sh` therefore tallies the trailing run in **two independent classes**, from the reason token in the comment lead alone (no tmux probe, no timestamps — it runs at cycle start and stays a pure comment-history reader): `incomplete-waiting` against a loose `WORKER_WAIT_LIMIT` (default 10), and **every** `**Worker interrupted:` plus every other incomplete reason (`uncommitted`, `unpushed`, `nopr`, `draft`) against the tight `WORKER_LIMIT` (default 4). A mixed run escalates only when one class reaches its own limit, and the escalation comment names which class tripped. The asymmetry is priced by **retry cost**, not by severity: an exit-to-wait retry reattaches, sees the job running, and exits for cents, where an `interrupted-*` retry already burned a full `WORKER_BUDGET` — and a worker that exited with uncommitted work or left the PR draft is a malfunction, not a handoff, so it must not ride the loose limit merely because its status is spelled `incomplete-*`. Rejected: a single higher limit (blunts the real-malfunction signal) and exempting `waiting` outright (reopens exactly this issue's hole — a tmux job alive but never finishing would re-dispatch forever, and patching that back needs a log-staleness heuristic with no defensible threshold; separate limits need no heuristic and never remove the backstop). Same amendment, on the reporting side: `incomplete-*` still outranks the verdict file in `watch-dispatch.sh` (a live session is the more urgent fact for anyone deciding whether to dispatch into that worktree), but an `incomplete-waiting` checker whose verdict file parses now reports **both** facts rather than discarding the verdict.

**Worker and checker are now symmetric: both roles post an interrupted *and* an incomplete lead** *(issue #52, 2026-07-31)*. `finalize_dispatch` posted `**Worker interrupted:` / `**Worker incomplete:` / `**Checker incomplete:` — and no `**Checker interrupted:`. A checker cut off mid-run therefore left **nothing countable**: it applied no verdict label and posted no round comment, so `NROUNDS` stayed frozen at zero and the next cycle dispatched another checker on the same ready PR, at a full `CHECKER_BUDGET` a round, with no path to `needs-input`. Not a corner case — rate-limiting is the likeliest cause of an interrupted checker, so the common failure was the unbounded one. This is the same hole #40 closed on the worker side, where `WORKER_LIMIT` deliberately counts "cut off" and "exited without finalizing" under **one** cap because both are an attempt that produced no finished work. Fix: the checker branch posts both leads (mirroring the worker branch, push-outcome note and all), and the three leads that constitute a checker round are enumerated **once** — `CHECKER_ROUND_LEADS` in `bin/dispatch-common.sh`, next to the code that posts two of them — with `orchestrator-cycle.sh` sourcing that file and counting through the shared `checker_rounds_this_generation` helper. Structural, not documentary: a future lead added to the poster is counted by construction, which the old private copy of the list in the cycle script could not promise. Deliberate non-goals: **no new knob** (interrupted rides the existing `CHECKER_LIMIT`, as on the worker side — the split there is priced by *retry cost*, and both checker classes cost a full `CHECKER_BUDGET`), and **no change to generation-reset semantics** (only a to-operator verdict — `pass` / `pass_with_findings` / `blocked` — ends a generation; `changes_requested`, `incomplete` and `interrupted` all decided nothing and merely accumulate). The escalation now says "rounds without a to-operator verdict" rather than naming verdicts alone. Covered by `tests/offline/test-checker-rounds.sh` (counting, generation reset, and the cap arithmetic against the script's own default) plus the poster cases in `test-finalize-complete.sh`.

**A ready PR that cannot merge is not finalized either: the `conflicting` rung** *(issue #51, 2026-08-02)*. The ladder above checks `waiting → uncommitted → unpushed → nopr → draft` and never consults **mergeability**, so a ready-but-`CONFLICTING` PR passes the entire battery: no live session, clean worktree, nothing unpushed, an open non-draft PR on `issue-N`. Observed 2026-07-31 — a round-3 worker on #40 exited, the launcher recorded `done`, and PR #46 was `isDraft: false` with `mergeable: CONFLICTING`; the digest then read it as a ready PR awaiting a checker, and a whole `CHECKER_BUDGET` round was spent discovering the conflict and bouncing it back. The loop *did* recover (digest → checker → bounce → `resume` → worker), so what this buys is stated narrowly: **one-round-earlier, far cheaper detection** — the worker's own exit says the PR cannot merge and posts one countable `**Worker incomplete: incomplete-conflicting` comment, instead of paying a checker to learn it.

`conflicting` is the ladder's **last** worker rung, deliberately: it is the only reason that can cost an *extra* network round-trip plus a retry, so every cheaper signal — including `draft` — gets to win first, and a draft PR makes no mergeability call at all. The checker ladder is unchanged (`waiting → noverdict`): a checker does not own PR mergeability.

The load-bearing subtlety is that **GitHub computes `mergeable` asynchronously.** For a few seconds after a push — exactly when a worker exits — `gh pr view --json mergeable` returns `UNKNOWN` while the test merge is recomputed. Two failure modes follow, and the design must dodge both. A naive strict check ("not `MERGEABLE` ⇒ conflicting") would stamp `incomplete-conflicting` on healthy work whenever the API lagged — the same false-positive class the `nopr`/`draft` rungs already guard against. A naive no-retry check would see `UNKNOWN` on nearly every healthy finish, always conclude "inconclusive," and never fire for real. So `_pr_mergeable` (a) asserts **only** on an explicit `CONFLICTING` — `MERGEABLE`, a stuck `UNKNOWN`, an unrecognized value, a non-zero `gh` exit and unparseable output all collapse to *inconclusive*, which yields "finalized" with a one-line stderr note — and (b) **re-polls `UNKNOWN`**, bounded at one poll plus 2 re-polls ~3s apart under a hard ≤10s wall-clock ceiling (checked *before* each sleep, so the sleeps are inside the ceiling) — a worker's exit path must never hang on GitHub. The knobs (`MERGEABLE_REPOLLS`, `MERGEABLE_POLL_SLEEP`, `MERGEABLE_POLL_CEILING`) exist so the offline tests exercise this same code with the sleeps zeroed; the defaults are the contract. **Do not "simplify" the permissive/retry behavior into a strict check** — that reintroduces exactly the false positive it was written to avoid.

`incomplete-conflicting` counts in the **hard** class against `WORKER_LIMIT`, not the loose `WORKER_WAIT_LIMIT`: a conflict is a real blocker needing action, not a cheap babysit handoff. That falls out of `ledger-prune.sh`'s classifier being *default-hard* (only the wait lead matches the wait regex), which is the intended polarity — a new reason token is hard-class unless deliberately exempted. The posted comment names the fix concretely (the PR is ready but unmergeable; merge `origin/main` into `issue-N`, resolve, commit, push) rather than just the status, because a bare status is what invited the round-3 failure of re-*verifying* the PR instead of resolving it.

*Same issue, one-line gap in the escalation comment:* when a trailing run trips **both** classes in the same prune, only the tripped class was named (it is checked first), so the other class's count silently vanished from the record the operator actually reads. `escalate_needs_input` now takes an `also` context line — still **one** comment per prune per issue, still naming the tripping class and its knob as the unambiguous trigger, with the other class reported as context ("Also in the same trailing run: N …, counted separately against `X`").

**The finalizer itself can die: reconcile-before-prune** *(issue #63, 2026-08-19)*. Everything above hardens the path where `finalize_dispatch` **runs**. It runs *inside* the dispatched session — `run_in_new_session` appends it to the trailing `bash -c` chain — so a session killed outright (SIGKILL, host sleep, OOM) never reaches it, and none of the machinery above fires: no status flip, no push, no countable comment. The line sits at `status dispatched` against a pid that is already gone, and `ledger-prune.sh` then **deleted it silently**, because its "surface a dispatch that did not finish cleanly" branch is gated on a status that *already* reads `interrupted-*`/`incomplete-*`, which a still-`dispatched` line never does. Observed 2026-08-04 on a checker (`california-pesticides` PR #64, pid 80838, 0-byte log): the review had **completed** — a full `pass_with_findings` verdict JSON on disk — but the label the brief has the checker apply *as its own last act* was never applied, so the PR never reached the operator's merge gate; nothing countable was posted, so `CHECKER_LIMIT` stayed frozen and the same PR was due to be re-checked at a full `CHECKER_BUDGET`; and the ledger returned to a clean state with the verdict orphaned in `logs/`. The label was applied by hand from the JSON. Same false-confidence family as #40/#49/#51/#52, but because the failure is that the finalizer *never runs*, the fix cannot be another rung inside `assert_finalized` — it has to live **outside the dispatched process**.

`bin/ledger-prune.sh` therefore runs three phases: **reconcile → sweep → prune**. Reconcile walks the ledger and, for every entry whose pid is dead and whose status never reached a terminal value, redoes the finalization: `classify_result` on the log, then the `assert_finalized` battery for its kind, with the result written to the line *before* any prune decision. It differs from `finalize_dispatch` in exactly one place, deliberately: **`unknown` gets the battery too.** `finalize_dispatch` consults it only after a `done` classification because it judges a process it just watched exit normally; a reconciler judges a process that was *killed*, so no result JSON was ever written and `unknown` is the expected classification for precisely the deaths it exists for — refusing the battery there would leave every reconciled entry at `unknown`, saying nothing about whether the deliverable landed, when the verdict JSON in `logs/` is exactly the evidence that decides it. A checker whose verdict file parses then has its routing **published from that file** — the label on the closing issue, the countable `**Checker verdict:` comment (on disk the findings are invisible to everyone), and for a worker-court verdict the PR flipped back to draft, which is not cosmetic: `board-digest.sh` strands a *ready* PR whose issue carries `resume` in **neither** bucket, so a label without the flip hands the work to nobody. Every other reconciled entry gets exactly what `finalize_dispatch` would have left — the stranded-commit push and the one countable `**Worker/Checker interrupted:|incomplete:` comment — so the caps finally advance for a death they used to be blind to. The verdict → label map lives in `verdict_label` (`bin/dispatch-common.sh`), the one copy outside `briefs/checker-brief.md`; the comment bodies are **not** copied at all but extracted into `report_no_clean_finish` and shared with `finalize_dispatch`, because the caps match on the *lead* and a drifted second copy would silently stop counting.

Three properties are load-bearing. **Idempotent:** every act reads state first — the label only when absent, the recovered comment only when the PR carries no `**Checker verdict:` comment at all (the checker may well have posted its own before dying), the draft flip only when the PR is currently ready — so a second reconcile publishes and posts nothing. **A completed review is not an incomplete round:** publishing is gated on the verdict parsing, not on the reconciled status, and when it publishes, *no* interrupted/incomplete comment is posted — the label is the outcome, and a countable "this round decided nothing" comment about a review that decided everything would burn a `CHECKER_LIMIT` round for a success. **Nothing is dropped in silence:** a live pid is never touched (its own `finalize_dispatch` is still coming) and a `-` pid (a `--foreground` dispatch) is unknowable and left alone, so a line that is still non-terminal at prune time is one reconciliation *could not* finalize — and it is now pruned with a warning naming the entry, its log path, and whether a verdict file is sitting there unread. The middle phase covers what the reconciler structurally cannot see: a verdict JSON whose ledger line was **already** dropped (by any prune that ran before this existed) is reported when its routing label never landed on a still-open PR — **report-only**, deliberately, since with no ledger entry there is no dispatch context (which generation, whether a later round superseded it) to act on safely, and bounded by `VERDICT_SWEEP_LIMIT` with a note when it truncates. One deliberate non-goal: the reconciler does **not** call `record_usage_reset`. That parser rolls a "resets 7:40pm" already past today's clock forward to *tomorrow* — honest seconds after a cutoff, a ~24h deferral of the whole loop when read off a log that died at an unknown time in the past. Covered by `tests/offline/test-ledger-reconcile.sh`, which runs against a **stateful** `gh` shim (labels and comments it applies are visible to the next lookup) so idempotence is genuinely tested rather than merely re-run.

*Two bugs that defeated this detection were fixed 2026-06-22* (recovery worked all along via the worktree+label self-healing above — but the **detection/recording half was silently dead**): (1) under `set -euo pipefail`, claude's **nonzero exit** on an interrupted run (budget cap / rate limit / error) aborted the launcher subshell *before* `finalize_dispatch` — i.e. it only ever ran on the clean exit-0 path where its interruption handling wasn't needed; fixed with `|| true` on the claude invocation in both the foreground and detached paths of both launchers. (2) `classify_result` read "the last non-empty log line," but the checker's `report_mutation` appends *after* the result JSON, so it parsed that prose and returned `unknown` — meaning a checker could never record `done`; fixed by scanning lines in reverse for the last `type=="result"` object. (Earlier "proven live" 429 recovery was real for *recovery*; the ledger `status`/warning it should have left was the part that wasn't landing.)

**Detached dispatches run in their own session** *(added 2026-06-22)*. A worker/checker dispatched by the headless orchestrator shared that orchestrator session's process group — so when the orchestrator exited, the teardown signal to its group reaped the in-flight worker *mid-run*, leaving work uncommitted and a **0-byte log** (the whole subshell was hard-killed before `finalize_dispatch`, so the interruption wasn't even recorded). Diagnosed live: launches isolated in a plain shell survived, but every worker dispatched *by the headless orchestrator* died — 2/2. Fix: `run_in_new_session` (in `bin/dispatch-common.sh`, used by both launchers' detached paths) runs the guarded command in **its own session** via a tiny `python os.setsid()` shim (macOS ships no `setsid(1)`); `exec` preserves the pid, so the pid recorded in the ledger *is* the session leader that `finalize_dispatch` later matches. The new-session body runs claude → (checker only) `report_mutation` → `finalize_dispatch`, all appended to the log. Verified: the leader gets its own pgid distinct from the launcher's and survives a launcher-group `SIGTERM`, and a real cycle-dispatched worker then ran to a clean, recorded finish. *(Foreground `--foreground` dispatches are supervised and unaffected — they aren't orphaned.)*

*This isolation does NOT survive tearing down the launchd job itself* *(issue #18, 2026-07-15)*. `setsid` detaches a dispatch from the launcher's **process group**, but a worker the autonomous cycle spawned still lives inside that launchd **job's** tree, and `launchctl bootout` — which is what `bin/schedule.sh pause` runs — SIGTERMs the whole job tree, reaping any in-flight worker/checker (observed: a `pause` killed a ~13-min build mid-run). Truly escaping the job's domain (double-forking into a separate launchd job) is fragile and high-blast-radius, so the fix is at the lever, not the isolation: `pause` now reads the ledger for live dispatches (status `dispatched` + a still-alive pid) and **refuses while any is in flight**, printing them and pointing at `status`; `pause --force` overrides and kills. The interactive brief documents pausing safely (drain first) since the interactive orchestrator and the autonomous cycle otherwise compete for the same board/worktrees.

## Safety model

Workers run unattended (no human to approve prompts), so guardrails are **defense in depth** — only the first layer trusts the model to behave:

**Layer 1 — OS:** `raw/` is **read-only** (perms / read-only symlink) — workers read `raw/`, write only to `processed/`/`out/` in the worktree; `--add-dir` scopes filesystem reach to just the worktree + data path. (For *dropbox-native* repos that can't be chmod'd without breaking coauthor scripts, this protection is delivered by the Layer-2 deny-hook over the manifest's `raw_paths` instead — see Portability.)

**Layer 2 — Claude Code (deterministic, harness-enforced):**
- `--permission-mode bypassPermissions` so workers never stall on an unanswerable prompt, **but**
- a **`PreToolUse` hook** *denies* dangerous calls before they run — `rm -rf`, writes outside the worktree, `git push … main`, force-pushes, and writes/deletes under the manifest's raw prefixes (`raw_resolved` + `raw_paths`). Certain prefixes are an explicit **allow-carveout** over that raw denylist — needed when a repo's writable paths live *inside* a shared raw tree. Three sources, all in `load_writable_prefixes()`: manifest **`output_paths`** (e.g. `distance-decay-est`'s per-survey `outputs/`/`results/` nested under the Dropbox-symlinked `07 Dataclean`); **`ORCH_LOGS_DIR`**, the orchestrator's own logs dir, which is runtime state rather than project data and must stay writable even when a self-hosting manifest's `raw_resolved` blankets the whole live clone; and manifest **`derived_resolved`** plus `<data_root>/derived`, the optional shared derived tree, which is writable *by design* because a worker whose issue is "build the panel" has to be able to write the panel. Each carveout is conditional on its source being configured — with `derived_resolved` unset, a write under `data/derived` in a repo whose `raw_paths` is `.` is still denied. **Author responsibility: never point a carveout inside real raw data**;
- a **`Stop` hook** refuses to let a worker finish until protocol is met (PR opened, results-summary present), feeding the gap back;
- `--disallowedTools` blocks destructive patterns; checkers additionally drop `Edit`/`Write` (see Checkers).
- **`Agent` (subagents) is denied in every *unattended* dispatch** *(issue #45)* — `bin/launch-worker.sh`, `bin/launch-checker.sh`, and the headless cycle orchestrator in `bin/orchestrator-cycle.sh`. Delegation escapes the protocol layer, not the data layer: a subagent runs with **no brief** (`briefs/*-brief.md` is the protocol — no PR contract, no results-summary, no verdict JSON, no escalation vocabulary), **no exit guard** (`host/hooks/worker-stop-guard.sh` binds the *main* session's `Stop`; a subagent's completion fires `SubagentStop`), and **no separate budget** (its spend lands on the same `--max-budget-usd`). Layer 2 itself still holds either way — a `--settings` `PreToolUse` hook *does* fire on a subagent's tool calls (verified), so `raw-data-guard.py` covers delegated work. `bin/launch-orchestrator.sh` is **deliberately exempt**: that session is human-present, so the operator sees each delegation, can interrupt it, and owns the spend; narrowing it would only cost the operator inspection power.
  - Why blanket, not a curated allow-list (verified on `claude` 2.1.220): `--disallowedTools Agent` removes the tool from the schema outright (`No such tool available: Agent`) rather than soft-denying it, but **"deny all but `Explore`" is not expressible** — `--allowedTools "Agent(Explore)" --disallowedTools "Agent"` still blocks everything, so keeping one agent requires *enumerating* every other (`Agent(referee)`, `Agent(paper-reader)`, …). An enumerated list fails **open** the next time an agent file lands in `~/.claude/agents/`, silently, inside an unattended `bypassPermissions` session; the blanket deny fails **closed** and needs no maintenance. If a worker is ever observed burning its cap on repo spelunking, re-admit `Explore` by *generating* the deny list at dispatch time from `{built-ins} ∪ ~/.claude/agents/*.md ∪ <worktree>/.claude/agents/*.md` minus a one-name allow-list — do not hand-enumerate it. (Residual gap even then: a new *built-in* agent in a future CLI version.)
  - Note `--disallowedTools` is **variadic**, so each call site keeps `Agent` inside its *single existing* flag and is followed by another `--flag`; a second `--disallowedTools`, or a trailing positional, would be parsed ambiguously. `tests/offline/test-agent-deny.sh` asserts the deny for all three dispatches.
- a **pre-dispatch raw-link gate** *(issue #35, defense-in-depth for #25)*: `bootstrap_worktree_data` (shared by both launchers) hard-fails a real dispatch **before `claude` is spawned** if a data-backed worktree's critical `data/raw` symlink is missing or dangling, so a worker/checker can never compute on missing inputs and exit 0 (the #25 silent failure). It only reads/stats paths (a legitimately-empty raw tree proceeds with a one-line note; a code-only manifest whose `raw_resolved` is the working clone is exempt), and `--dry-run` never reaches it.

**Layer 3 — GitHub (server-side backstop):** branch protection requires a PR and forbids direct pushes to `main`. Even a fully rogue agent with the token **cannot** corrupt `main` or self-merge. *Caveat (found 2026-06-19):* GitHub gates branch protection on **public repos or a paid plan** — on a **private free-plan repo** (most research repos, e.g. `solar-income`) the API returns 403 and this layer is **unavailable**. Where it's off, the bulletproof guarantee is gone and Layer 2's push-to-`main`/force-push denials are the only thing keeping a worker off `main` (model-trusted only insofar as the hook's pattern-matching is complete). For private repos that need the real server-side guarantee, options: GitHub Pro; make the repo public; or give the worker a **feature-branch-scoped token/deploy key** that physically cannot push to `main`. To confirm per repo: `gh api repos/<owner>/<repo>/branches/main/protection` (403 = unprotected).

**Layer 4 — budget:** a per-session `--max-budget-usd` cap on every role + the orchestrator's concurrency cap bound runaway cost. Each role's cap is tunable *(per-role budgets added 2026-06-22)*: the launchers default to **worker $10.00** (`bin/launch-worker.sh`, raised from $4.00 on 2026-07-01 after a legitimately large multi-spec issue hit the old cap mid-run) and **checker $3.00** (`bin/launch-checker.sh`), overridable per dispatch by the `--budget` arg, or session-wide by the `WORKER_BUDGET` / `CHECKER_BUDGET` env vars (precedence: `--budget` arg > env > default). `bin/orchestrator-cycle.sh` reads `WORKER_BUDGET` / `CHECKER_BUDGET` (same defaults) and threads them into every checker call and the worker dispatch line, so a single env var raises the ceiling for a whole cycle. The **orchestrator** session itself is capped by `BUDGET` (default $2.00, raised from $0.50 on 2026-07-14) and pinned to a cheap `MODEL` (default `sonnet`) — it only reads the digest and routes, so it needs neither a frontier model nor a large cap.

Two lessons are baked into that pairing, both learned when a dry-run cycle with two live candidates dispatched nothing *(2026-07-14)*:

- **Pin the model, or the cap is meaningless.** The cycle originally passed no `--model`, so the headless session silently inherited the operator's interactive default — at the time, Opus with the 1M-context window, billing at long-context premium rates where a *single* turn can cost ~$0.26. A $0.50 cap is a two-turn budget under those rates, and the orchestrator was killed mid-decision. A budget cap only means something if the price per turn is pinned too; otherwise changing an unrelated interactive default silently re-tunes the whole loop.
- **A killed session must not look like an idle one.** `--max-budget-usd` termination returns JSON with `is_error`, `errors`, and `terminal_reason: budget_exhausted` — and **no `result` key**. The result parser defaulted that missing key to the string `(no result)`, which reads exactly like "the orchestrator considered the board and found nothing to dispatch." The parser now branches on `is_error` and prints the error and terminal reason. Note the cap is enforced *between* turns, so actual spend overshoots it (the killed run cost $0.5372 against a $0.50 cap): treat it as a stop signal, not a hard ceiling.

The **orchestrator** gets its own guardrails: board-only (no `--add-dir` to any data), no `Edit`/`Write`, its own budget cap — it can dispatch and label, nothing else.

**Interactive orchestrator — post-dispatch watch (`Monitor` grant)** *(added 2026-07-23, issue #26)*. The human-gated interactive orchestrator now watches the workers/checkers it dispatches to terminal state **automatically**, reporting outcomes as they land, so the operator no longer types "watch them" every session. It does this by running the deterministic **`bin/watch-dispatch.sh`** — which owns the local-signal detection (one line per dispatched item the instant it goes terminal, exits when all are, and reports `unknown` on a dead-but-unfinalized pid so a crash is never watched in silence) — under the harness **`Monitor`** tool, whose stdout streams as chat events without blocking the session; where `Monitor` is absent it runs the same script **blocking**, with identical semantics. The watch reads only **local** signals — a `ledger.md` `status` field flipping off `dispatched` (→ `done` / `interrupted-*` / `unknown`) and the checker's `logs/<slug>-pr-<n>-verdict.json` appearing — so it costs **zero GitHub calls per tick**; it resolves the authoritative GitHub outcome with a single `board-digest.sh` / `gh pr view` call once per terminal event. Granting `Monitor` **widens** the `/orchestrate` command's `allowed-tools` from "board digest + two launchers + read-only `gh`" to also include arbitrary background shell — a deliberate `allowed-tools` widening (high-blast-radius per CLAUDE.md), acceptable **only** because this front is human-present. It is confined to the two interactive fronts: the `/orchestrate` frontmatter (explicitly added) and the launcher-booted session (whose unrestricted interactive scope already includes it — `bin/launch-orchestrator.sh` sets no `--allowedTools`, so nothing there is narrowed). The **autonomous/scheduled** orchestrator (`briefs/orchestrator-brief.md`, `bin/orchestrator-cycle.sh`) deliberately does **not** get this: it runs one-shot `claude -p`, which exits before `Monitor` events could arrive, and it monitors across cycle invocations by design.

**The merge gate protects the decision, not the keystroke** *(added 2026-08-02, issue #48; prompted by the PR #47 merge on 2026-07-31)*. The interactive brief used to forbid merging in absolute terms ("non-negotiable"), which produced the wrong failure mode in practice: PR #47 was `checked-pass`, mergeable, CI green, and *read by the operator*, who said "merge it for me — this passes the human merge gate" — and got a policy discussion plus an ad-hoc mid-session exception instead of a merge. What the gate actually protects is the **decision** (a human judged the outputs worth landing), not the **mechanics** (typing `gh pr merge`). Those are now separated in `briefs/orchestrator-interactive-brief.md`: the human-gated orchestrator may merge only when the operator instructs it **in that session, naming the PR**, and the PR is `checked-pass` on its linked issue (or the operator explicitly waives that); it never merges on its own initiative, never reads a dispatch-batch "go" as merge authorization, and never folds a merge into a batch. **One instruction authorizes exactly the named PR** — the same shape as "a single 'go' authorizes exactly that batch" — and it must report the post-merge state (PR `MERGED`, linked issue `CLOSED`) so the operator sees the outcome without opening GitHub. The **default is unchanged**: absent an instruction, a `checked-pass` PR is surfaced and never acted on. Two deliberate limits: the **autonomous** brief (`briefs/orchestrator-brief.md`) carries the prohibition as absolute — it runs unattended, so no instruction can exist and nothing (a `checked-pass` label, a green check) may be read as one; and `gh pr merge` is **not** added to the `/orchestrate` command's `allowed-tools`, so even an authorized merge surfaces a permission prompt naming the exact command — a second, harness-level confirmation, and the reason this affordance needs no `allowed-tools` widening at all. This is a protocol-layer change only: no script merges, no launcher grew a `--merge` flag.

**Standing guards (hygiene backstop, brief-layer)** *(added 2026-07-13)*. Beyond the destruction-safety layers above, both briefs carry a fixed integrity/hygiene bar every PR must clear regardless of what its issue asked for — because the guards live in the protocol layer, not individual issues: (1) no secrets/credentials/absolute local paths/PII in the diff, (2) the changed entry point runs clean from a fresh session, (3) seeds set where sampling/simulation/bootstrap is introduced, (4) affected docs updated (or a stated "no docs needed" reason), (5) raw inputs untouched. The worker self-verifies 1–4 and attests in the results-summary (guard 5 is already covered worker-side by the raw-data rules + deny-hook); the checker independently verifies 1–5 on every PR, and a violation is an `actor=worker` finding that bounces the PR (`changes_requested`/`fail`) even when the issue's explicit criteria all pass. This is model-trusted on the worker side and independently checked — not a harness-enforced layer.

## Running the cycle

Every command for running the system by hand — one full pass, previewing the board
digest, dispatching a single worker/checker, reclaiming worktree disk — plus the
tunable env vars (`CAP`, `BUDGET`, `WORKER_BUDGET`, `CHECKER_BUDGET`, `CHECKER_LIMIT`,
`WORKER_LIMIT`) lives in the [README](README.md) (*Usage*), which is the single source
of truth for operating the system. This design doc explains only *why* the cycle is
shaped as it is: the ledger/worktree prune → checkers → workers ordering falls out of

## Scheduling & power

The schedule fires the **cycle**, not a bare `claude -p`. The real entrypoint is `bin/run-cycle.sh` (a launchd-safe wrapper around `bin/orchestrator-cycle.sh`); `bin/schedule.sh` installs/manages the launchd agent and the wake chain. (The `bin/schedule.sh` subcommands themselves — `install`/`live`/`plan-only`/`run`/`status`/`pause`/`resume`/`uninstall` — are documented in the [README](README.md) *Enable the scheduled loop* / *Day-to-day scheduler commands*; this section is the design rationale behind them.)

- **Wake:** a macOS **`launchd`** agent (label from `orchestrator.conf`'s `LAUNCHD_LABEL`, rendered from the `host/LaunchAgents/orchestrator.plist` template into `~/Library/LaunchAgents/` by `bin/schedule.sh install`) fires `bin/run-cycle.sh` at `StartCalendarInterval` slots — by default **night-heavy centers 20/23/02/05/08** — to shift the grind off the daytime session-limit window. launchd (over `cron`) runs a missed slot once on wake. The slots are the **single source of truth** `SCHEDULE_SLOTS` in `orchestrator.conf` (space-separated 24h `HH:MM`): `bin/schedule.sh install` *generates* the plist's `StartCalendarInterval` block from that list (the template ships a `@CALENDAR_INTERVAL@` marker, no literal fire times) and seeds the pmset wake chain from the same list, so wake and fire can never desync — changing the cadence is a one-line config edit + re-`install`. An unset value falls back to the night-heavy default; a malformed slot fails loud rather than rendering a broken plist.
- **Jitter (±15 min):** launchd has no native jitter, so synchronized on-the-hour fires would stampede shared servers in lockstep with everyone else's cron. The plist therefore fires **15 min early** (:45 of the prior hour) and passes `--jitter`, which makes `bin/run-cycle.sh` sleep a random **0–30 min** (`caffeinate -i` holds the Mac awake through it) — so each cycle actually starts uniformly within **±15 min of its center**. Jitter applies only to scheduled fires; manual `bin/schedule.sh run` and any `--dry-run` are immediate. Window is `JITTER_MAX_SECS` (default 1800).
- **`bin/run-cycle.sh`** does the three things a bare schedule gets wrong: (1) sets a known **PATH** (launchd's stripped env can't find `claude`/`gh`/the python.org `python3`); (2) the **usage gate** (below); (3) arms the next pmset wake so the chain self-perpetuates. It tees a human log to `logs/cycle.log`.
- **Usage-limit gate (overnight lever):** dispatches run on Emmett's Claude **subscription** (no API key), so they share his **5-hour rolling session limit** — overnight work shifts *when* the pool is spent, freeing the daytime window (it doesn't add quota; a *weekly*-cap hit can't be helped by timing). There is **no way to query the reset ahead of time** — Claude only reveals it *reactively*, as prose in the 429 result (`"resets 7:40pm"`). `record_usage_reset` (in `bin/dispatch-common.sh`, called from `finalize_dispatch` on a worker/checker rate-limit and from `bin/run-cycle.sh` for the orchestrator session) parses that into `state/usage-reset`; `bin/run-cycle.sh` then **defers** any fire inside the exhausted window (a skipped fire costs nothing) and resumes automatically once the marker passes.
- **Manual trigger:** a hand-run cycle kickstarts the agent through the *identical* launchd path (not a separate code path), so what you test by hand is what fires on the timer; a `--dry-run` variant plans inline without spending. Status inspection surfaces the same state the scheduler acts on — agent state, next pmset wake, the usage gate, and the cycle-log tail.
- **Plan-only → live is a toggle, not a plist edit:** the mode lives in `state/mode` (machine-local), which `bin/run-cycle.sh` reads on every fire; missing/non-`live` → plan-only, so a fresh install never dispatches for real until you opt in. Flipping it (via the README's `live`/`plan-only` subcommands) needs no file editing and no `launchctl` reload — effective on the next cycle. An explicit `--dry-run`/`ORCH_DRY=1` still forces plan-only regardless. Pausing/resuming stop and restart firing entirely (lighter than uninstall; for being away). **Plan-only is a *mechanical* gate, not just advice to the planning model** *(issue #18, 2026-07-15)*: a plan-only cycle passes `--dry-run` into `bin/orchestrator-cycle.sh`, which exports `ORCH_PLAN_ONLY=1`; both dispatch launchers honor that by **forcing `--dry-run` on themselves**, so the headless orchestrator (run with `bypassPermissions`) cannot spend even if it omits the flag. Before this, plan-only only *told* the model to pass `--dry-run` — and a plan-only cycle was observed launching a real worker when the model didn't, contradicting the mode's own "spend nothing" description.
- **Per-repo autonomous allow-list (`state/scheduled-repos`)** *(issue #27)*: a second, *finer* off-switch than the global `state/mode`. `state/mode` decides whether the loop spends **at all**; the allow-list decides **which onboarded repos** it may spend on. Polarity is **allow-list-when-set**: the file lists the LIVE slugs (one per line), so **empty/absent ⇒ every onboarded repo dispatches autonomously** (backward-compatible — the pre-#27 behavior), and **non-empty ⇒ only the listed slugs do**. A repo left off the list is *scheduler-paused*, not offboarded — it keeps its manifest and stays fully dispatchable by **manual** `launch-worker.sh`/`launch-checker.sh` and **interactive** `/orchestrate`; only the **unattended** loop skips it. Scope is therefore *automated-loop-only*, and by construction: the gate lives entirely in `bin/orchestrator-cycle.sh` — applied at **both** the `SLUGS` computation feeding the worker brief **and** the checker loop — so it covers every autonomous pass whether fired by `run-cycle.sh` (cron) or run by hand, while the manual launchers (which never read the file) are untouched. Reading the list is centralized in **one** sourced helper (`scheduled_repos` in `bin/config-common.sh`) so `orchestrator-cycle.sh`, `board-digest.sh` (which annotates paused repos `⏸ scheduler-paused`), and `bin/schedule.sh enable/disable/status` can't drift. `enable <slug>` validates the slug is onboarded (a manifest exists) before adding it; a listed slug whose manifest later disappears is ignored with a warning, never dispatched. A **newly onboarded repo is excluded from the cron loop until `enable`d** whenever a non-empty allow-list is in effect — onboarding no longer implies autonomous spend. The file is machine-local and gitignored (all of `state/`), like `state/mode`; the empty-file case is normalized to "absent" (`disable` removes the file once it empties) so the two encode the same all-live default. Bash 3.2 traps from CLAUDE.md are respected — the reader branches on emptiness rather than expanding an empty array, and the predicate helper's exit status is only ever consumed in a conditional.
- **Concurrency cap:** start at **2–3** workers (`CAP`), tied to *your review bandwidth*, not CPU.
- **Sleep & power (honest):** launchd won't wake a sleeping Mac on its own. `bin/schedule.sh install` seeds **`pmset`** wakes — a daily `repeat wakeorpoweron MTWRF` bootstrap plus a self-arming one-off `schedule wake` before each slot (pmset holds only one *repeat*/day, hence the chain). Needs the Mac **on power**; a closed lid still sleeps between wakes, which is fine — it wakes ~2 min before each slot, fires, and sleeps again. In-flight workers freeze if the Mac sleeps mid-run; the next cycle recovers them via worktree reuse + retained label. True 24/7-while-closed would want a dedicated always-on host.

## The inbox

**Not** an LLM-generated markdown (rejected: stale/hallucination risk, duplicates truth). Instead:

- **A saved board view "Needs Me"** — filtered to (`needs-input` ∨ PR-ready-for-merge ∨ `needs-definition`), **grouped by the Project field**. Deterministic, *is* the truth, every row clicks straight to the work. You clear one project fully, then switch domains once.
- **A batched push** twice a day (sit-down + evening) with deterministic counts from the digest script — e.g. *"Pesticides: 2 merge, 1 answer · Energy: 1 define."* No per-event pings (that recreates babysitting). One real-time exception: the orchestrator itself crashed / everything blocked.

## Response handshake

The orchestrator never interprets your prose. **Comment = content (for the worker to read); label = signal (for the orchestrator to route on).**

- **Answer an escalation:** post comment **+** swap `needs-input` → `resume`. Next wake: digest sees `resume` → dispatch worker → `/pickup` → reads your answer → continues → clears label.
- **Send a PR back:** comment your question + un-ready the PR + `resume`.
- **Merge:** you click merge — or tell the interactive orchestrator to merge the PR you name (terminal either way; board auto-moves to Done via existing workflow).
- **Define a bounced issue:** you + advisor console write the acceptance criteria/outputs; it becomes dispatch-ready.

The advisor console can do the comment + label flip in one step when you say "post this to #N."

## Intake gate

When the orchestrator considers dispatching, it judges whether the issue carries a real contract (goal, acceptance criteria, defined outputs). If materially under-specified, it **does not dispatch** — it labels `needs-definition` and drops it in your inbox. It never drafts the content itself (no intent). The orchestrator may auto-answer only **mechanical** escalations (e.g. obvious repo routing); anything substantive passes straight to you — a wrong auto-answer is worse than a question.

## Label vocabulary (proposed — redline me)

The determinism of the whole loop rests on these. Digest script keys on:

- `needs-input` — worker/checker escalated; your court (answer).
- `resume` — you've answered (or a checker requested changes); worker's court. *(As of 2026-07-01, no longer load-bearing for dispatch: `bin/board-digest.sh` derives worker's-court status structurally from PR draft/live-worker state, so a crashed-before-labeling worker is still picked up. The label is now a legibility aid — set for humans scanning the plain issue list — not the dispatch signal itself.)*
- `needs-definition` — the orchestrator's verdict after evaluating: under-specified; your court (author criteria).
- `hold` — *your* pre-emptive "not ready, don't dispatch." The digest **hard-excludes** it (no orchestrator judgment). Chains with the above: `hold` while you draft → remove it → orchestrator then either dispatches or bounces with `needs-definition`.
- `blocked` — waiting on something external.
- *Work vs review* is carried by **PR draft/ready state**, not a label.

## Portability & bootstrap

The system splits into portable and machine-local parts; the goal is that a new machine (or project) is reproduced from the repo + GitHub, never from memory.

- **Portable (this repo + GitHub):** design, scripts, templates (including the sanitized per-project manifest template, `templates/project.yml`), briefs, hooks, skills — plus GitHub-side state (labels, the board view, branch settings).
- **Machine-local — the bits that "make it tick":** Claude Code hook/permission config (`~/.claude/settings.json`), the rendered `launchd` plist (`~/Library/LaunchAgents/`), the per-operator identity config (`orchestrator.conf`, gitignored — operator name / GitHub handle / PR owner / launchd label / board number so a labmate runs their own instance; loaded and validated by `bin/config-common.sh`, scaffolded from the tracked `orchestrator.conf.example`), user skills (`~/.claude/skills/`), the out-of-Dropbox working clones, `gh`/Dropbox auth, and the **filled-in per-project manifests** (`projects/*.yml`, gitignored — they carry real repo names, local clone/data paths, and confidentiality notes).

To make the machine-local pieces reproducible, their canonical copies live **in the repo** (`host/`, `templates/`, `orchestrator.conf.example`) and are wired into place from there — never symlinked into `~/.claude/`: the host hooks are passed to each dispatch by in-repo path, the `launchd` plist is rendered by `schedule.sh`, and the identity config is scaffolded from its tracked example.

- **`bin/install.sh`** — host bootstrap: checks deps (`gh`, `jq`, `claude`, `python3`, `git`) + `gh` auth, marks the in-repo host hooks + launcher scripts executable, creates `logs/`+`state/`, scaffolds `orchestrator.conf` from the tracked example, and renders the one opt-in `~/.claude/` file (the `/orchestrate` command — carve-out below). It registers **no hooks and no default behavior** in `~/.claude/` — the *host* hooks (worker/checker safety) are passed to each dispatch by in-repo path (`--settings`/hook flags), never into a shared `~/.claude/settings.json`, so interactive Claude Code sessions elsewhere on the machine stay untouched. The `launchd` plist is installed separately by `bin/schedule.sh install` (needs sudo, so it's opt-in). (The new-machine sequence — clone → `install.sh` → `gh auth login` → fill `orchestrator.conf` — is in the [README](README.md) *Install*.)
- **`bin/test.sh` + `tests/`** — the shell layer's test suite (surfaced as `dr test`; it grew out of and replaced the earlier single bootstrap-check script, which had quietly become the de-facto test file). Two tiers under `tests/`: an **offline** tier (`tests/offline/`, deterministic, no network/`gh`, always runs and must pass) and an **online** tier (`tests/online/`, exercises real `gh` and `SKIP`s cleanly when offline). Shared helpers live in `tests/lib/` — an assertion lib (`pass`/`skip`/`fail` + `assert_*`) and a sandbox helper that stands up a throwaway `mktemp` `ORCH` so no test touches a real `orchestrator.conf` or project data (a pre-existing real conf is asserted byte-identical entry→exit). The runner discovers `test-*.sh` files, runs each via `bash <file>` (so adding one needs no `+x`/`install.sh` change), tallies PASS/SKIP/FAIL, and exits nonzero **iff an offline test fails**. Offline coverage: the identity guard in all three states + `{{OPERATOR_NAME}}` brief render; the `derailleur`/`dr` dispatcher incl. symlink resolution; `watch-dispatch.sh` classification; `tmux-run.sh` name/log/`--tail`/mutex; the `scheduled_repos` allow-list reader + `schedule.sh enable`/`disable`; `worktree-prune.sh --auto --dry-run` (the bash-3.2 regression net) and its dead-`derail-*` tmux-session reaper (private-socket isolated; SKIPs without `tmux`); and `ledger-prune.sh` dead-pid pruning. CI (`.github/workflows/ci.yml`) runs the offline tier on `macos-latest` — whose runner still ships **bash 3.2** — on every push/PR, so the real compat constraints are exercised rather than papered over on a Linux/bash-5 runner. (README → *Verify / test suite*.)
- **The `~/.claude/` carve-out — `/orchestrate`.** The one thing derailleur writes under `~/.claude/` is a slash-command file, `~/.claude/commands/orchestrate.md`, rendered by `install.sh` from the tracked template `templates/orchestrate.command.md` with this checkout's absolute path baked into `{{DERAILLEUR_ROOT}}` (idempotent; rewrites only on content change). It is **safe by construction**: a command file is *inert until the operator types `/orchestrate`* — it registers no `SessionStart`/`PreToolUse`/`Stop` hook, so it alters no default session behavior anywhere; its `allowed-tools` is scoped to exactly the board digest, the two launchers, read-only `gh`, and the `Monitor` tool for post-dispatch watching (never blanket `Bash` — see the safety-model note on the `Monitor` grant); and it can only *propose* — the human-gated brief requires an explicit confirmation before any dispatch, and the one merge path it has (an in-session instruction naming the PR, above) is both operator-initiated and, because `gh pr merge` is deliberately absent from that `allowed-tools` list, permission-prompted on top. This is why the carve-out doesn't violate the worker-hook-isolation principle above: worker *safety* hooks still never leak into normal sessions; only an opt-in, read-mostly convenience command does. One portability guard on that render: because `orchestrate.md` bakes in an absolute path it must never be committed, so `install.sh` resolves the render target through symlinks (`pwd -P`) and warns loudly when it lands inside a git work tree — some dotfiles setups symlink `~/.claude/commands` into a versioned repo, and a committed copy would carry one machine's home directory and dead-end `/orchestrate` on every other machine that pulls it. It warns rather than hard-fails (the file renders fine; the danger only materializes on commit). (README → *Install*.)
- **`bin/new-project.sh <repo>`** — per-project onboarding: creates labels, ensures the board view covers it, sets up the out-of-Dropbox working clone, scaffolds the manifest.
- **`README.md`** — getting-started guide: host + per-project checklists, including the irreducibly-manual steps (board-view membership, Dropbox "available offline" pinning, coauthor buy-in for shared-repo branch protection).

**Per-project manifest** (`projects/<repo>.yml`) is the onboarding unit — repo, board Project, archetype, clone/worktree locations, data root, and the raw-path deny-list. The manifests themselves are **machine-local (gitignored)** since they carry real repo names, local paths, and confidentiality notes; what's *tracked* is the sanitized shape in `templates/project.yml`, which `bin/new-project.sh` renders into a fresh manifest. So onboarding on a new machine is `bin/new-project.sh` (scaffold from the template) + filling its TODOs — or copying an existing manifest across by hand.

**Project archetypes** (a manifest field):
- **git-native** (preferred) — repo is git-only; `data/` is a symlink to a Dropbox location (or in-repo if small/non-restricted). Worktrees trivial; raw protected by perms or the deny-hook.
- **dropbox-native** (legacy/coauthored, e.g. solar-income) — repo lives in Dropbox; workers operate from an out-of-Dropbox clone; raw pinned "available offline" + protected by the deny-hook. Used when coauthors require the Dropbox-native layout.

## Build order (de-risked: conventions first, automation last)

- **Phase 0 — conventions, manual dry-run** ✅ *(solar-income pilot; full loop proven by hand → PR #4 merged)*. Labels, results-summary template, raw-data deny-hook, worker launcher; per-project manifest as the onboarding unit. (Branch protection is unavailable on private free-plan repos — Layer-3 gap below.)
- **Phase 1 — digest script + hook** ✅. `bin/board-digest.sh` + env-gated `SessionStart` hook + `bin/launch-orchestrator.sh`. The digest reports (board state, in-flight ledger diff, dispatch candidates with acceptance criteria, the PR review-pipeline); the orchestrator decides. **Two human-gated interactive fronts** share one role brief (`briefs/orchestrator-interactive-brief.md`, token-free, rendered verbatim by both — distinct from the autonomous Phase-4 `briefs/orchestrator-brief.md`): `bin/launch-orchestrator.sh` (boots a session in this checkout with the digest pre-injected) and the `/orchestrate` slash command (callable from *any* repo, whole-board or `/orchestrate <slug>`-scoped via the digest's optional slug filter). Both **propose, then dispatch workers *and* checkers only on the operator's explicit confirmation** — never autonomously, and never merge on their own initiative (merge only on an in-session instruction naming the PR — see Safety model, 2026-08-02).
- **Phase 2 — worker harness** ✅. `bin/launch-worker.sh` + `briefs/worker-brief.md`: headless worker on one issue with worktree, deny-hook, safety flags, budget cap; draft PR + results-summary contract; fresh session per dispatch.
- **Phase 3 — checker** ✅ *(built & proven)*. `bin/launch-checker.sh` + `briefs/checker-brief.md`: an LLM checker on a ready PR, restricted to Read/Bash/`gh` (no Edit/Write) + a launcher-side mutation baseline; emits the structured verdict JSON and routes by **actor of the remaining findings** (worker-actionable → `resume`; only Emmett's calls left → `checked-pass`), with a `CHECKER_LIMIT` round backstop. `bin/orchestrator-cycle.sh` dispatches it deterministically on ready, not-yet-passed PRs. Validated end-to-end on solar-income PR #5 (worker↔checker round-trips converged to `checked-pass`). The **`Stop` hook** (worker exit-contract enforcement, above) is built & unit-validated 2026-06-21. (Per-push GitHub Actions CI dropped — see Checkers: no cloud data to run against.)
- **Phase 4 — orchestrator automation** ✅ *(scheduled launcher built; ships in plan-only mode)*. `bin/orchestrator-cycle.sh` (prune → dispatch checkers → dispatch workers up to `CAP`) + `bin/ledger-prune.sh`; the scheduled launcher is `bin/run-cycle.sh` + `bin/schedule.sh` + the `host/LaunchAgents/orchestrator.plist` template (label from `orchestrator.conf`), with a night-heavy schedule, a pmset wake chain, and the subscription usage-limit deferral gate (above). Mode (plan-only vs live) is a machine-local toggle in `state/mode`, flipped by `bin/schedule.sh live`/`plan-only` (no plist edit); default plan-only.
- **Phase 4.1 — resilience hardening** ✅ *(2026-07-01, prompted by issue #16 stranding after a budget-cap interruption)*. Three gaps found by tracing that failure end-to-end: (1) `bin/board-digest.sh` derives worker's-court status structurally from PR draft/live-worker state instead of requiring a `resume` label to have been written at exactly the right moment — closes the "first-attempt crash, no label to inherit" hole; (2) `finalize_dispatch` now pushes local commits and posts a `**Worker interrupted:` issue comment immediately on any hard stop, rather than waiting for a future redispatch to notice; (3) `WORKER_LIMIT` (default 4, mirrors `CHECKER_LIMIT`) counts consecutive interruption comments and escalates to `needs-input` instead of retrying forever. - **Phase 4.2 — reporting honesty** ✅ *(2026-08-03, issue #49)*.
