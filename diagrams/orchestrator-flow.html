FSE Research orchestrator — system diagram

How an issue becomes a merged PR

The full dispatch loop, one issue's journey from creation to Done — who acts at each step, and where the loop has actually broken.

Actor Emmett Orchestrator Worker Checker GitHub (automatic)
Node judgment call deterministic script
STEP 1 Emmett

An issue enters the system

Emmett (occasionally a worker filing a follow-on) opens an issue in an onboarded repo with a goal and - [ ] acceptance-criteria checkboxes. A global PostToolUse hook auto-adds it to the FSE Research board (project #3); Emmett sets Project and an initial Status (usually Backlog or Up Next).

⚠ Routing only works if the repo's label set exists — see known issue: label bootstrap.
STEP 2 Orchestrator · script

The cycle wakes up

A launchd agent fires run-cycle.sh → orchestrator-cycle.sh on a schedule (night-heavy slots: 20/23/02/05/08) or by hand. If Emmett's Claude session limit is currently exhausted, the cycle defers itself rather than dispatching into a 429.

STEP 3 Orchestrator · script

Housekeeping

ledger-prune.sh drops ledger entries whose issue is closed or whose pid is dead; worktree-prune.sh reclaims disk from merged/closed branches. For a pruned entry whose status was interrupted-*, it counts consecutive **Worker interrupted: comments on the issue (posted by Step 7c) — below WORKER_LIMIT it leaves recovery to Step 5's structural dispatch; at the limit it escalates straight to needs-input.

✓ Revised 2026-07-01: this used to be the only place that made a crashed worker dispatchable again (by relabeling resume) — a single-point-of-failure if it ever missed its moment. See resolved: worker retry cap.
STEP 4 Orchestrator · script

Checker dispatch pass

Purely mechanical, no LLM involved: for every ready (non-draft) PR whose issue isn't already checked-pass / resume / needs-input, and that hasn't hit CHECKER_LIMIT (default 4 rounds this review generation), launch a checker via launch-checker.sh in its own detached session. A ready PR is the request to be checked — no judgment needed to see that.

→ hands off to Step 8 · Checker session
STEP 5 Orchestrator · script

Board digest

board-digest.sh reads the board, the ledger, and every open PR across onboarded repos, and buckets everything: Needs Emmett (needs-input, needs-definition, checked-pass), Dispatch candidates — resume (any draft PR with no live worker and not needs-input/hold/blocked, derived structurally from PR + ledger state, not from a label) plus actionable-with-no-open-PR — and In review (ready PRs awaiting a checker only; a stalled draft is no longer parked here). This is a report, not a decision — no LLM runs yet.

STEP 6 Orchestrator · LLM

Intake gate & dispatch

A headless Claude session boots with the digest injected, capped at the remaining worker slots (CAP, default 2) and its own $0.50 budget. It walks only the Dispatch-candidates section, resume issues first: well-specified + onboarded + not held/blocked → launch-worker.sh. Under-specified → labels it needs-definition and moves on, no guessing.

✓ Fixed 2026-07-01: this brief still forbids acting on "In review," but a stalled draft PR isn't filed there anymore — Step 5 now hands it over as a normal resume candidate. See resolved: stalled PRs.
→ hands off to Step 7 · Worker session
STEP 7 Worker

Worker session

launch-worker.sh boots a worker in a reused-or-created git worktree (issue-N branch), in its own detached process group so it survives the dispatching session's teardown. Guarded by a raw-data write-block, a Stop hook, and a $10.00 budget cap. It reads the issue (and any PR review comments, if resuming), does the work, commits as it goes, and opens a draft PR early. It ends in exactly one of three states:

a. Ready for review

Marks the PR ready, fills in the results-summary (goal / what I did / what I ran / key outputs / judgment calls / outcome), clears resume if it was addressing feedback.

→ Step 8 · Checker
b. Blocked

Adds needs-input + a specific question as a comment; PR stays draft. The Stop hook requires one of these two exits before it lets the session end.

→ Step 9 · Emmett's inbox
c. Interrupted (hard stop)

Budget cap, rate limit, or crash ends the process directly — no clean exit, so the Stop hook never runs. finalize_dispatch classifies the result, pushes any local commits immediately (doesn't wait for a future redispatch), and posts a **Worker interrupted: <status> issue comment.

→ recovery via Step 5, next cycle
✓ Fixed 2026-07-01: the Stop hook still can't see a hard stop, but finalize_dispatch now handles it directly (push + comment above), and WORKER_LIMIT caps repeated interruptions the way CHECKER_LIMIT caps the checker loop. See resolved: hard interruption and resolved: worker retry cap.
STEP 8 Checker

Checker session

Triggered by Step 4, including immediately after 7a. launch-checker.sh boots with Read/Bash/gh only — no Edit/Write, and a mutation baseline (git status --porcelain) checked on entry and exit. It verifies each acceptance criterion against the real outputs — re-running scripts, not trusting the PR's claim — and tags every finding actor: worker (a fixable bug) or actor: emmett (a judgment call). It never fixes anything; it emits one structured verdict:

a. pass / pass_with_findings

Criteria met; any remaining findings are all actor: emmett. Labels checked-pass, leaves the PR ready.

→ Step 9 · Emmett's inbox
b. changes_requested / fail

At least one actor: worker finding. Un-readies the PR, labels resume.

→ Step 7 · Worker
c. blocked

Can't judge without a human — access missing, spec unintelligible. Labels needs-input, leaves the PR ready.

→ Step 9 · Emmett's inbox
Backstop: rounds are counted per review generation (reset once a verdict reaches Emmett). At CHECKER_LIMIT (4) rounds without converging, Step 4 escalates straight to needs-input instead of checking again — a worker↔checker ping-pong can't run forever.
STEP 9 Emmett

Emmett's inbox

Everything that needs a human judgment call lands here — via the advisor console (an interactive in-repo Claude session) or raw gh commands:

needs-definition

Emmett writes concrete acceptance criteria into the issue body, clears the label.

→ back into Step 5's actionable pool
needs-input

Emmett answers the question as a comment and relabels resume — content and signal, the same handshake in both directions.

→ Step 7 · Worker
checked-pass

Emmett reviews the PR. Either merges it, or sends it back with a comment (+ un-ready and resume).

→ Step 10 or back to Step 7
STEP 10 GitHub · automatic

Merge & close

Emmett merges — branch protection (where the plan supports it) makes this literally the only way code reaches main. GitHub auto-closes the issue via Closes #N; the board's built-in "PR merged → Done" workflow moves the card automatically. No script of ours runs this step. Loop ends for this issue.

Known fragility points

Everything below was found by reading the code, not assumed. All five were closed the same day they were found (2026-07-01) — kept here as the record of what broke and why, not a to-do list.

WhereWhat was wrong, and the fixStatus
Step 1 · setup-labels.sh

A repo added via a project manifest without going through new-project.sh never got the required label set — every routing label failed silently. glyphosate-neonatal-health was onboarded this way and was missing 5 of 6. Fix: ran setup-labels.sh (idempotent, safe to re-run on any onboarded repo).

 Fixed
Step 5 · board-digest.sh

A draft PR with no live worker and no label ("stalled") sat in the In-review section, which the orchestrator's brief explicitly forbids it from touching — yet nothing else owned that state either. Issue #16 was stranded here after a budget-cap interruption. Fix: dispatch eligibility is now derived structurally from PR + ledger state (draft, no live pid, not needs-input/hold/blocked) instead of requiring a label — no more court with no owner.

 Fixed
Step 7 · dispatch-common.sh

The Stop hook that enforces "leave a PR or a needs-input label" only fires on a voluntary session end — a budget-cap or rate-limit kill terminates the process directly, so the enforcement never ran. Fix: finalize_dispatch now handles the hard-stop case itself: pushes local commits immediately and posts a **Worker interrupted: comment, with no dependency on the hook.

 Fixed
Step 3 · ledger-prune.sh

The checker loop has CHECKER_LIMIT (4 rounds) as a backstop against endless ping-pong; there was no equivalent cap on a worker that keeps getting interrupted on the same issue. Fix: WORKER_LIMIT (default 4, same mechanism) counts consecutive **Worker interrupted: comments and escalates to needs-input at the limit.

 Fixed
design.md · Worker lifecycle

The design doc stated the orchestrator "detects a dead process with no ready signal → flags as stuck, retries once." No such logic existed in the scripts — the doc described intent, not behavior. Fix: the section now describes the actual push+comment+WORKER_LIMIT mechanism above, with the old claim struck through in the doc's own history note.
